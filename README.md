# AIOps Mission Control — Marconi100 demo dashboard

A working demo that drives the "AIOps Mission Control" mockup with **real failure-prediction
models replayed over real historical data**. There is no live cluster: a virtual clock replays
the September-2022 test period. Every number shown is either a real model prediction on real
data, a real IPMI/SLURM measurement, a clearly-labelled proxy, or an explicit `N/A`.

```
dashboard/
  app.py                 FastAPI app + endpoints ($PORT/0.0.0.0 entrypoint, /health, in-memory policies)
  models.py              data access over the precomputed store (reads DEMO_DB; applies live policies)
  replay.py              virtual-clock replay engine (stateless, wall-clock-derived + manual override)
  precompute.py          one-off: score the whole test period offline -> data/demo.sqlite
  make_demo_edition.py   one-off: curate the full store -> data/demo_lite.sqlite (deploy artifact)
  requirements.txt       pinned serve-time dependencies (excludes the offline-only heavy libs)
  render.yaml            Render free-tier blueprint (native Python web service)
  .gitignore             keeps the 490 MB data/demo.sqlite out of git
  data/
    demo.sqlite          full store (~490 MB, git-ignored, local only)
    demo_lite.sqlite     slim 3-day edition (~48 MB, committed, served by default)
    hero_examples.json   guided-tour anchors (hero IDs + virtual timestamps to jump to)
    model_info.json  meta.json  policies.json    model/metadata/default-policy config
  static/index.html      the modified mockup (live, polls the API)
  README.md              this file
```

## Run it

**To serve the app**, only the pinned serve-time deps are needed (no modelling libraries — the app
runs no inference at request time):

```bash
pip install -r requirements.txt
```

To also **rebuild the databases** (`precompute.py`) you additionally need the offline stack
(`duckdb pandas numpy pyarrow scikit-learn lightgbm joblib`); those are deliberately *not* in
`requirements.txt` (see **Deployment** below).

The operations report (below) can be narrated by the Anthropic API. This is **optional** — without
it the report is generated by a deterministic template. To enable the LLM narration:

```bash
pip install anthropic
export ANTHROPIC_API_KEY=sk-ant-...     # never commit this; it is read only server-side
# optional: export REPORT_MODEL=claude-haiku-4-5-20251001   (the default)
```

Then start the app **from this `dashboard/` directory** and open the browser:

```bash
uvicorn app:app --reload
```

By default the app serves the slim **`data/demo_lite.sqlite`** (3-day window). To serve the full
store instead, point `DEMO_DB` at it:

```bash
DEMO_DB=data/demo.sqlite uvicorn app:app --reload     # full 10-day period, ~490 MB, local only
```

Open <http://127.0.0.1:8000>. Interactive API docs at <http://127.0.0.1:8000/docs>;
liveness at <http://127.0.0.1:8000/health>.

> The replay clock is **live by default**: its position is derived from wall-clock time (looping
> through the window), so any worker — or a cold-started free-tier instance — shows the same sensible
> mid-window moment rather than snapping to the start. The header controls (pause/play, step +15 min,
> reset, speed, scrubber) layer an in-memory override on top; that override is per-process and simply
> falls away on restart, returning to the shared live position.

The databases are already built. To rebuild them from the read-only source data (`D:/M100/data` +
the P2/P3 artifacts in `D:/M100/P2`): `python precompute.py` writes the full `data/demo.sqlite`;
then `python make_demo_edition.py` curates it into the committed `data/demo_lite.sqlite`.

## The two models (both real, both shipped)

| | **P3 — Job outcome** | **P2 — Node anomaly** |
|---|---|---|
| Predicts | at SLURM submit: FAILED / TIMEOUT / OUT_OF_MEMORY vs COMPLETED | a node monitoring-anomaly onset within 30 min |
| From | job metadata + expanding-window user history | IPMI sensor telemetry (363 features) |
| Model | HistGradientBoosting, multi-class → `1 − P(COMPLETED)` | LightGBM |
| Metrics | **ROC 0.871 · PR 0.726**; @0.30: precision 0.592 / recall 0.709 / F1 0.646 | **ROC 0.848** full population |
| Operating point | threshold **0.30** (WARN) — adjustable in Policies | **low-power risk triage**: score only the riskiest ~25% of node-slots → **ROC 0.926** |
| Source notebooks | `P3_02_job_outcome_model.ipynb`, `P3_04_coldstart_and_two_tier.ipynb` | `P2_09_full_scale_rebuild.ipynb`, `P2_10_imbalance_experiment.ipynb` |

`precompute.py` **re-derives both models from the source data and asserts they reproduce the
published metrics** (P3 ROC 0.871 / PR 0.726; P2 full-pop 0.848; P2 risk-filtered ≈ 0.926) before
writing the store — so the demo cannot silently drift from the notebooks.

### The P2 risk filter (the node model's default operating mode)
"Low power = risk": a node about to trip a monitoring anomaly is going **idle / dropping out**,
not overheating. The triage keeps the lowest-power slots by a single pre-`t` indicator
(`cur_ps0_inputP`, PSU-0 input power), with percentile cutoffs **derived on the training period
and applied to test**. Keeping the riskiest ~25% (PSU-0 ≤ ~286 W) lifts ROC 0.848 → ~0.926 at
essentially unchanged onset recall. The **filter strength is a Policies setting** and changes which
nodes are scored live.

## What is real vs. proxied vs. unavailable

**Real model predictions (on real data):**
- Job risk % and predicted failure type (Failed / Timeout / OOM) — P3.
- Node P2 risk score and the low-power triage — P2.

**Real measurements:**
- Job id / user / SLURM state / requested & elapsed walltime / partition / qos — from `job_table`.
- Node temperature / power / fan / ambient — from IPMI (`cur_g0_cT`, `cur_g1_cT`, `cur_totP`, `cur_fan0_0`, `cur_amb`).
- Auto-healing log wall — generated from **real events** (anomaly onsets, job flags at submission, job endings, with the model shown right *or* wrong).

**Proxy (labelled as such in the UI):**
- Utilisation % — derived from node total power vs a p99 reference. There is no direct GPU-utilisation channel joined into the node model.

**`N/A — not in dataset`** (rendered explicitly, never fabricated):
- **VRAM usage** — needs NVIDIA DCGM per-GPU memory telemetry.
- **PCIe error rate** — needs DCGM/NVML XID + PCIe replay counters.
- **MIG status** — M100 GPUs are V100 (no MIG; MIG is an A100/H100 feature).

`GET /api/model_info` returns this list in full — it is the honest "what data would we need"
answer, surfaced in the Policies tab under *模型資訊與資料透明度*.

### Honest caveats (also shown in the UI)
- **OOM is under-predicted.** SLURM memory-request columns are null in this dump, so the model
  rarely fires the OOM class as the top failure type — the OOM warning count is usually 0.
- **User 393 excluded.** A broken auto-resubmit script (45.8% of raw jobs at ~100% failure) is
  excluded from the job cohort, exactly as in the shipped model.
- Marconi100 nodes are **IBM Power9 AC922 + 4× NVIDIA V100**, not NVIDIA DGX. The mock's
  DCGM/DGX/MIG labels are kept for layout but marked `N/A` where the data cannot fill them.

## Replay window
- **Full store** (`data/demo.sqlite`): `2022-09-19 10:36 → 2022-09-29 18:57 UTC` — the P3
  out-of-sample test period, which overlaps the P2 node scores. 34,068 scored jobs · 748,238
  node-slots (826 nodes) · 840 real anomaly onsets.
- **Slim edition** (`data/demo_lite.sqlite`, the default served DB): `2022-09-26 → 2022-09-29 UTC` —
  a curated 3-day slice chosen for event density (highest confirmed-job-failure load in the period,
  ~2.8k non-completed endings incl. ~1.1k TIMEOUTs, plus 10 genuine isolated node onsets). 14,199
  jobs · 64,050 node-slots (825 nodes) · 10 onsets. The window travels with the DB (a `demo_meta`
  table), so the clock automatically replays whichever store is served.

## Endpoints (all JSON, documented at `/docs`)
| Endpoint | Purpose |
|---|---|
| `GET /api/summary` | dashboard KPIs and current counts at virtual time |
| `GET /api/nodes` | node rows (`?limit=`, `?sort=risk\|temp\|power\|node`) |
| `GET /api/jobs` | job rows (`?limit=`, `?state=`, `?sort=risk\|elapsed\|submit`) |
| `GET /api/logs` | recent auto-healing / event log lines |
| `GET /api/jobs/{job_id}` | **drill-down**: one job's real input features, model output, and (global) attribution |
| `GET /api/nodes/{node_id}` | **drill-down**: a node's real IPMI inputs, output, and per-prediction contributions at the current virtual time |
| `GET`/`POST /api/clock` | read / control the replay (play, pause, step, reset, speed, jump, jump_frac) |
| `GET`/`POST /api/policies` | read / update settings **in memory** (never written to disk) |
| `POST /api/policies/reset` | restore the seeded default policies (in memory) |
| `GET /api/model_info` | model names, metrics, training windows, feature counts, methodology, and the explicit unavailable-fields list |
| `GET /api/report` | auto-generated operations report at the current virtual time — params `window` (lookback hours), `lang` (`en`/`zh`), `length` (`brief`/`full`); returns the generated `text`, the `mode`, and the underlying `facts` JSON |
| `GET /api/heroes` | guided-tour anchors (hero IDs + virtual timestamps to jump to), from `data/hero_examples.json` |
| `GET /health` | liveness probe → `{"status":"ok"}` |

### Policies actually change the tabs
- **Alert threshold** (P3, default 0.30) → changes which jobs are flagged and the warning counts.
- **Node filter strength** (P2, default riskiest 25%) → changes which nodes are scored.

Both are applied server-side on every request, so moving a slider in the Policies tab is
immediately visible on the Dashboard / Jobs / Nodes tabs.

## Input/output drill-down (click any Jobs or Nodes row)
A side panel opens with three clearly-separated blocks (labelled in both languages):
- **INPUT** — the *real* feature values fed to the model for that row. Job: requested walltime,
  nodes, GPUs, partition, QoS, submit hour/weekday, and the user-history features with their
  values at submission (null → shown as *median-imputed*). Node: current & rolling temperature/
  power/fan, z-scores vs the node's own 7/30-day baseline, and rack-neighbour context.
- **OUTPUT** — the risk score, predicted class (jobs) / triage scope (nodes), the operating
  threshold in force, and whether the row is currently flagged.
- **WHY** — for the **P2** node model, real *per-prediction* LightGBM feature contributions
  (`pred_contrib`, signed log-odds); for the **P3** job model, the model's **global** permutation
  importance shown against this row's values — **explicitly labelled as global importance, not
  per-prediction attribution.**

Every value in the panel is the real stored feature value. `precompute.py` computes and stores
the top-15 P3 input features per job, and the top-8 per-prediction contributions + curated input
features per node-slot; it also **asserts the LightGBM model reproduces the saved score
(max\|diff\| < 1e-5)** so the contributions are honestly from the model that made the prediction.
A panel line states *when* the prediction was made (job: at submission; node: at the 15-min slot)
and that it used only information available at that moment.

## Language toggle (EN / 中文)
A header toggle re-labels the entire UI without reloading. Chinese is the default; the choice is
persisted in `localStorage`. Implemented as one translation dictionary with `data-i18n` tags plus
a `t()` helper used by the dynamic renderers — a single page, not a duplicate. A **How this works**
button (header) opens a bilingual box explaining the offline-train → precompute → replay pipeline.

## Auto-generated operations report (`report.py`)
The sidebar **AIOps Agent** box and the **Generate shift report** panel are written from the real
system state at the current virtual time. The split is strict and mandatory:

1. **Facts are computed in Python, never by the LLM.** `assemble_facts()` reads only real values
   from `demo.sqlite` for a virtual time + lookback window: jobs submitted / flagged / ended and
   the FAILED/TIMEOUT/OOM breakdown; prediction outcomes in the window (**correct warnings, false
   alarms, and — reported honestly — misses**, with counts and example IDs); node anomaly onsets
   with node IDs and times; nodes currently carrying high P2 risk with their sensor readings; the
   highest-risk running/queued jobs; and the operating settings in force.
2. **The LLM only narrates those facts.** `generate_llm()` sends the facts JSON with an instruction
   to use only the supplied values, invent nothing, compute no new ratios, report misses, and phrase
   actions as recommendations for a human to approve (never as actions taken). **The output is then
   numerically validated** — every numeric token in the generated text must map to a number in the
   facts (`unverified_numbers()`); if any does not, the LLM text is discarded and the template is used.
3. **Template fallback.** `render_template()` produces the same five-section report (Situation /
   What happened / Current risks / Recommended actions / Model note) from the identical facts with
   **no LLM at all**, so the feature works fully offline. The response's `mode` field says which
   path produced the text (`llm`, `template`, or `template_llm_rejected`), and the UI shows a badge.

The report **respects the language toggle** (en/zh) and comes in two lengths: `brief` (the Agent
box, refreshed as the clock advances, throttled to ~12 s and cached) and `full` (the shift-report
panel, with **copy to clipboard**, **download as `.md`**, and a collapsible **raw facts JSON** so
the evidence behind the prose is one click away).

### Agent reply shapes, and the platform-side instructions you must also update

The LaplaceAI agent is configured **platform-side** with its own system instructions. Two things
follow, and the second one is easy to lose an afternoon to:

* **Both reply shapes are handled here.** If the agent is configured with a *JSON contract* it
  returns an object such as `{"executive_summary": "...", "risk_assessment": "..."}`. `report.py`
  parses that and composes the markdown itself (`compose_narration()` → `compose_markdown()`), so
  presentation stays under Python's control: each key becomes a section heading (`executive_summary`
  → “Executive summary”; unknown keys are title-cased and appended rather than dropped), and list
  values become bullets. A plain-markdown reply is passed through unchanged. For `length="brief"`
  the result is flattened to **one plain-text paragraph with no markdown**, because the sidebar
  element is written with `textContent` and would otherwise show the syntax literally.
* **A reply that is not report content is rejected.** `_meta_commentary_reason()` applies a small,
  deliberately conservative set of signals — self-referential preamble (“I have generated…”,
  「我已…」), any mention of producing/attaching/downloading a **file**, a response in the wrong
  language for the request, or a near-empty reply. On rejection the deterministic template is served
  with `mode = "template_llm_rejected"` and a `fallback_reason` naming the cause. The numeric
  guardrail then runs on the **composed** text, so validation is never bypassed by this step.

### Endpoint resilience, and the pre-demo prewarm

A LaplaceAI **504** is a gateway timeout on *their* side — the agent exceeded its internal limit, so
raising the client timeout cannot help. Three things absorb it:

* **Retries.** Transient failures (502/503/504/408/429/500, read timeout, connection error) are
  retried up to **3 attempts** with exponential backoff plus jitter, bounded by a hard
  **150-second** total ceiling so a report request can never hang indefinitely. Auth (401/403) and
  malformed-request (other 4xx) failures are **not** retried — they are configuration errors.
* **Error-class-aware cooldown**, replacing the old flat 120 s breaker: **25 s** after transient
  failures (short enough that you are not stuck in template mode), **15 min** for auth, **10 min**
  for malformed requests. While cooling down, `fallback_reason` says so explicitly with the cause
  and the remaining seconds — `endpoint cooling down after HTTP 504 (18s remaining)` — so it is
  never mistaken for a missing key or a numeric rejection.
* **A trimmed prompt payload.** The agent receives a narration-sized view of the facts (example
  arrays capped at 2, list sections at 4, epoch duplicates and the other language's caveat dropped):
  **3,726 → 2,740 characters, 26 % smaller**, and 17 % off the whole prompt. The **full** facts are
  still used for the numeric guardrail and the raw-facts panel, so a report quoting something that
  was trimmed out of the prompt still validates.

**Before a demo, prewarm the cache** so the demo path never depends on a live call:

```bash
python prewarm_reports.py            # live: walks the hero timestamps + a spread, both languages,
                                     # both lengths, and writes data/report_cache.json
python prewarm_reports.py --mock     # same path with the agent stubbed (no network) - for a smoke test
python prewarm_reports.py --clear    # drop the prewarm cache
```

Only `mode == "llm"` results are written, so a prewarmed entry is by construction one that passed the
hard gate. The in-memory cache lives in one process, so the prewarm file is what makes a *separately
run* script useful to the server: on a cache miss the app reads `data/report_cache.json`, and those
entries ignore the short TTL. Every filesystem operation degrades silently, so a read-only deployment
behaves exactly as before. A mock run of 7 timestamps × 4 combinations produced 28 entries in 5.7 s;
a live run costs roughly the agent's own latency (~1 min) per entry.

> **⚠️ The prompt alone cannot override the agent's platform-side system instructions.** `report.py`
> now states the language requirement twice (top and end of the prompt) and forbids preamble,
> self-introduction, file/download/attachment references and non-string values — but if the agent is
> configured on the LaplaceAI platform to emit a download card, to answer in a fixed language, or to
> wrap replies in commentary, **it will keep doing so and the reply will be rejected here**. Update
> the agent's own system instructions to match: return report content only, in the language named in
> the request, with string values only and no file references.

**Key handling & safety.** The Anthropic key is read only from `ANTHROPIC_API_KEY`, server-side,
never hardcoded or sent to the client. If the SDK is not installed or the key is absent, the code
skips straight to the template without erroring. LLM calls use `max_retries=0`, a 15 s timeout, and
a 2-minute circuit breaker, so a missing/broken endpoint never hangs the polled report. **Only
successful (`mode == "llm"`) reports are cached** — a fallback is a transient condition, so pinning
one for the TTL would keep serving a bad report after the cause was fixed; fallbacks are retried on
the next request, and `GET /api/report?nocache=1` forces a fresh generation. Successful reports are
cached by (virtual-time bucket, window, language, length, thresholds) with a short TTL, so repeated
polling does not trigger repeated API calls.

## Deployment (Render, free tier, native Python — no Docker)

The app is built to run on a read-only, ephemeral, sleep-when-idle free instance.

**New files that make this work**
| File | Role |
|---|---|
| `make_demo_edition.py` | Curates the 490 MB `demo.sqlite` into `data/demo_lite.sqlite` (~48 MB) + `data/hero_examples.json`. Narrows to the 3-day high-event window, keeps every job overlapping it, keeps all nodes (onset nodes at full 15-min cadence, quiet nodes thinned to hourly), preserves every drill-down feature value, and `VACUUM`s. |
| `data/demo_lite.sqlite` | The committed, served database (well under GitHub's 100 MB limit). Carries its own replay window in a `demo_meta` table. |
| `data/hero_examples.json` | Three guaranteed "hero" moments (a caught high-risk TIMEOUT, a node flagged before a real onset, and an honest miss) with the virtual timestamps to jump to. Served at `GET /api/heroes`. |
| `requirements.txt` | **Serve-time deps only**, pinned: `fastapi, uvicorn, pandas, numpy, pydantic`. `duckdb / scikit-learn / lightgbm` are **excluded** — they are imported only by `precompute.py`, never by the serving app (which does zero inference), so leaving them out keeps the free-tier build small and fast. `anthropic` is excluded too (LLM report is local-only; deployment is template-only). |
| `render.yaml` | Render blueprint: `type: web`, `runtime: python`, `plan: free`, build `pip install -r requirements.txt`, start `uvicorn app:app --host 0.0.0.0 --port $PORT`, `healthCheckPath: /health`, and `DEMO_DB=data/demo_lite.sqlite`. |
| `.gitignore` | Keeps the 490 MB `data/demo.sqlite` (and `.env`, `__pycache__`, checkpoints) out of git. `demo_lite.sqlite` and `hero_examples.json` are **not** ignored — they must ship. |

**What the app already does for read-only / ephemeral hosting**
- **Port/host:** binds `0.0.0.0` on `$PORT` (default 8000); nothing hardcodes 8000.
- **Database:** path from `DEMO_DB` (default `data/demo_lite.sqlite`); queried per request against SQLite — the store is **never loaded into memory** — with indexes on the time-window and ID lookup columns.
- **Policies:** held in memory, seeded from `policies.json` at startup; `POST /api/policies` and `/api/policies/reset` never touch disk.
- **Clock:** derived from wall-clock time (see *Run it*), so a cold-started instance shows a live, consistent moment instead of resetting to the window start.
- **Report:** template-only without `ANTHROPIC_API_KEY` — no API call is attempted, nothing errors, and the UI badge reads **“Template (offline)”**. The LLM path stays in the code, inert, for local use.
- **Health:** `GET /health` → `{"status":"ok"}` for the platform probe.

**Deploy**
1. Commit this `dashboard/` folder as the repo (or set the service `rootDir` to it). Confirm `data/demo.sqlite` is git-ignored and `data/demo_lite.sqlite` (~48 MB) is tracked.
2. On Render: **New → Blueprint**, point at the repo; `render.yaml` provisions the free web service.
3. First request after idle cold-starts in a few seconds, then serves instantly.

**Edit-and-redeploy loop**
Change code or the UI → commit → push. Render auto-deploys. To refresh the demo *data* (different
window, different thinning), edit the constants at the top of `make_demo_edition.py`, run it locally
against the full `demo.sqlite`, commit the regenerated `data/demo_lite.sqlite` + `data/hero_examples.json`,
and push. No model retraining is involved — the predictions are precomputed and never change.

## Notes
- No model inference runs in a request handler — the API only reads the SQLite store, so the demo feels instant.
- The virtual clock's default position is stateless (wall-clock-derived); manual controls are per-process. Run one worker on the free tier.
- Windows: if the port is stuck from a previous `--reload` run, start with `--port 8010`.
